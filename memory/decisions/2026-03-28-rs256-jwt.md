# Decision — RS256 JWT for gateway authentication

| Field | Value |
|-------|-------|
| **Date** | 2026-03-28 |
| **Status** | Accepted |
| **Deciders** | Prometheus core team |
| **Related spec** | [memory/specs/002-jwt-authentication-middleware.md]../specs/002-jwt-authentication-middleware.md) |

---

## Context

The Prometheus gateway exposes an inference API that proxies to an unauthenticated llama.cpp
server. Any request that reaches llama.cpp is effectively trusted. We need an authentication
mechanism for service-to-service calls (client applications → gateway) that:

1. Works without a shared secret between the gateway and each client application.
2. Supports multiple client identities with independent claims/scopes.
3. Allows the gateway to validate tokens **without a live call to the auth server** on every request.
4. Supports key rotation without gateway redeployment.

## Decision

**Use RS256 (RSA + SHA-256) signed JWTs**, issued by an OAuth2 Authorization Server using the
**client credentials grant**, and validated by the gateway using the server's public JWKS endpoint.

## Rationale

### Asymmetric vs symmetric algorithms

| Property | HS256 (symmetric) | RS256 (asymmetric) |
|----------|------------------|--------------------|
| Key distribution | Shared secret — every client needs the key | Only the auth server holds the private key |
| Client compromise radius | Compromised client leaks the signing key | Compromised client leaks only its own `client_secret` |
| Gateway can verify without calling auth server | Yes | Yes (public key from JWKS) |
| Key rotation | Requires re-distributing to all parties | Gateway fetches updated JWKS automatically |

RS256 wins on the key distribution and rotation axes. In a multi-client environment (multiple
containerised apps), sharing an HS256 secret with every client is operationally risky.

### JWKS endpoint

The gateway fetches the OAuth2 server's JWKS (`/.well-known/jwks.json`) and caches it.
Cache is invalidated on `kid` miss (unknown key ID) → forces a refresh without gateway restart.
This enables seamless key rotation.

### Client credentials grant

Service-to-service calls have no interactive user. The client credentials grant issues tokens
bound to a `client_id` (application identity) rather than a user. The gateway extracts both
`sub` (user/service principal) and the custom `client_id` claim for rate limiting and metering.

### Algorithm pinning

The JWT library is explicitly configured to only accept `RS256`. This prevents:
- **Algorithm confusion attacks** (`alg: none`) — the parser rejects unsigned tokens.
- **HS256 substitution attacks** — if the gateway's public key were used as an HS256 secret.

## Consequences

- **Positive**: gateway validates tokens locally (no auth server round-trip per request).
- **Positive**: key rotation is zero-downtime and requires no configuration change.
- **Positive**: client credential compromise is limited in blast radius.
- **Negative**: requires an OAuth2 Authorization Server to exist (external dependency).
- **Negative**: RS256 token validation is slightly slower than HS256 (RSA math vs HMAC).
  Acceptable given llama.cpp inference latency is orders of magnitude larger.

## Rejected alternatives

| Alternative | Reason rejected |
|-------------|----------------|
| HS256 JWT | Key distribution risk in multi-client environment |
| API keys (static) | No expiry mechanism; revocation requires a database lookup on every request |
| mTLS | Complex certificate management; high operational overhead for dev environment |
| No auth | Unacceptable — llama.cpp has no auth layer; gateway must be the enforcement point |
